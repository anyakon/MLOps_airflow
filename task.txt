Цель задания: получить
практику оркестрации переобучения модели в Apache Airflow. Задание развивает
ваш сервис скоринга фродовых транзакций из предыдущих домашних заданий: чтение
потока из Kafka и выдача скора остаются, поверх них появляется DAG, который по
расписанию обучает модель и публикует новый бинарник в работающий сервис.

Для
выполнения рекомендуется изучить практическую часть занятия 7. Код семинара
загружен на GitHub: https://github.com/NikitaMalykhin/mlops_realtime_fraud_detector_airflow . По нему видно, как поднять Airflow рядом со скорингом,
как DAG публикует модель и как сервис её подхватывает.

Можно
опираться на свою кодовую базу с прошлых заданий или на код семинара. Сдаётся
ваш публичный репозиторий. Контракт скоринга менять не нужно: сервис
по-прежнему читает сообщения с транзакциями и отдаёт скор и флаг фрода. Тяжёлая
архитектура модели не требуется, обучение и inference выполняются на CPU.
Качество модели не оценивается.

Требования к реализации (не пугайтесь, они уже выполнены
в примере с семинара):

·
В docker-compose.yml
вместе с уже существующими сервисами скоринга поднимается Apache Airflow.
Сервисы находятся в одной сети. Airflow имеет доступ к данным для обучения и к
каталогу, откуда сервис скоринга читает модель.

·
DAG переобучения
описан кодом и состоит из нескольких задач с явными зависимостями. Одна
функция, которая делает все шаги без графа задач, не засчитывается.

·
DAG запускается по
расписанию. Чтобы проверку не нужно было ждать сутками, допустимо частое
расписание, например раз в 5 минут. Пропущенные запуски догонять не нужно:
catchup выключен. Ручной запуск из UI Airflow тоже должен проходить.

·
Цепочка задач как
минимум такая: подготовить обучающую выборку, обучить модель, сохранить файл
модели в каталог, смонтированный в сервис скоринга.

·
После успешного
прогона DAG в этом каталоге появляется новый файл модели, и сервис скоринга
считает скор моделью из каталога.

·
В результате
скоринга, помимо score и fraud_flag, есть версия модели, которой посчитан скор.
Версию должно быть видно в сообщении Kafka или в таблице результатов.

·
README.md описывает,
как поднять проект, где открыть UI Airflow, как запустить DAG и как убедиться,
что новые транзакции скорятся опубликованной версией модели.

·
По инструкции из
README не должно возникать проблем с поднятием контейнеров и проверкой DAG.

·
docker-compose.yml
поднимает стабильно работающие контейнеры скоринга и Airflow.

·
DAG переобучения виден
в UI, задачи связаны в цепочку, ручной запуск завершается без ошибок.

·
После запуска DAG в
общем каталоге появляется новый файл модели.

·
Сервис скоринга
считает скор моделью из этого каталога.

·
В результате
скоринга есть версия модели.

·
README позволяет повторить
запуск и проверку без устных пояснений.

·
Отдельный DAG по
расписанию дописывает в размеченную витрину новый месяц: берёт выборку уже
лежащих строк, переносит transaction_time в следующий календарный месяц и
добавляет батч в витрину. Наблюдения старше заданной глубины истории удаляются.
На семинаре глубина — 3 года, размер батча — 100 тысяч строк. Свои значения
нужно указать в README.

·
Окно обучения
скользящее: новый месяц добавляется в датасет, самый старый месяц из окна
убирается. Число месяцев в окне фиксировано. На семинаре в окне три месяца, вы
можете использовать другое

·
Разбиение на train и
test делается по времени: более ранние месяцы окна идут в обучение, самый
свежий месяц — в проверку. Случайный split не подходит.

·
Повторный запуск
после ошибки не пропускает месяц и не сдвигает окно второй раз. Указатель
месяца обновляется только после успешного сохранения модели.

·
Сервис скоринга
подхватывает новый файл модели без перезапуска контейнера.

·
Функции задач лежат
в отдельных модулях, а в файле DAG остаётся сборка графа. У функций есть
docstring: что задача читает, что записывает и почему повторный запуск не
должен испортить данные.

Оценивание работы

Оценка 6-7 баллов

Проект
загружен в репозиторий GitHub, и при проверке выполняются все пункты ниже.

·
В DAG реализован ваш собственный препроцессинг, а не
копия с семинара

Оценка 8-10 баллов

Реализованы
дополнительные требования:

·
В проекте
реализована логика проверки улучшения модели: если метрики свежей модели ниже,
чем предыдущей версии, то она не должна раскатываться на prod (не должна публиковаться). Продумайте, как бы вы считали
эти метрики и опишите логику в README

·
Создайте еще один DAG файл,
который реализовывал бы проверки вашего датасета на соответствие Data Quality требованиям. Результаты проверки необходимо публиковать в
виде html репорта в
отдельной директории рядом с директорией расположения модели. Требования должны
быть сформулированы и описаны в README (минимум 5 правил DQ).

Исходный код вашего
